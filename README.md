# mc-bot — ИИ-бот для Minecraft (DQN + Mineflayer)

## Цель проекта

Самообучающийся ИИ-бот для Minecraft на PyTorch. Этап 1 — базовая
локомоция: ходьба, повороты, прыжки через препятствия, подход к цели.

## Архитектура

```
Minecraft ← Mineflayer (Node.js) ── ZeroMQ PUSH/PULL ──→ Python (PyTorch, DQN)
```

- **Node.js** (`js/`) — поднимает **рой ботов** (`bot.count` в config.json,
  имена по паттерну `<username><separator><index>`: `AI_1`, `AI_2`, ... (`_`, а не `#`: ник с `#` не принимают команды сервера — `/op`, `/team`);
  при count=1 имя без суффикса), каждый бот шлёт состояние в Python с
  пометкой `bot_id` и применяет действия, адресованные ему. ВНИМАНИЕ:
  ванильный Minecraft допускает в никнеймах только `[a-zA-Z0-9_]` — если
  сервер не пускает ботов с `#`, поставь `bot.separator: "_"`.
- **Python** (`py/`) — у каждой **задачки** (walking, looking, follow,
  gathering...) свой «мозг»: параллельные DQN-сети по одной на **канал**
  («орган»: ноги, голова, руки — см. «Пространство действий») и своя
  память опыта. На каждого бота своя «сессия» (задача, стек кадров, цель),
  а мозг задачки общий для всех ботов, которые её делают, — опыт роя
  стекается в одно обучение (почти линейное ускорение набора опыта).
- Связь — ZeroMQ PUSH/PULL: Node → Python порт `5555`, Python → Node порт `5556`.
  Python делает `bind`, поэтому **запускать его первым**.

## Конфигурация — единый `config.json`

Все настройки (включая FOV, разрешение сетки зрения, дальность, параметры
обучения и наград) живут в `config.json` в корне. Обе стороны читают
только его — рассинхрон настроек между js и py невозможен по построению.

```jsonc
{
    "fov": 70,                       // поле зрения, градусы
    "vision": {
        "resolution": [8, 8],        // сетка лучей resX × resY (64 луча)
        "distance": 2,               // дальность в чанках (×16 блоков)
        "tick_delay": 2              // зарезервировано
    },
    "hearing": { "sectors": 8, "radius": 16 }
}
```

## Установка

```
npm install
pip install -r requirements.txt
```

PyTorch ставится отдельно — команда зависит от версии CUDA драйвера
(`nvidia-smi` покажет максимум), точную команду бери с селектора на
pytorch.org. Проверка: `python py/test_gpu.py`.

## Сервер-арена (`server/`)

Отдельный сервер Paper 26.1.2 только для обучения (и чтобы автор мог
поиграть с ботами в салки): кнопка **«Сервер»** в лаунчере (его лог —
в общем логе, галочка «Сервер»; при закрытии лаунчера сервер, запущенный
из него, останавливается с сохранением мира) или `server\start.bat`.
Команды серверу — в строке команд лаунчера с `/` в начале (`/gamemode
spectator`, `/time set day`...): уходят по RCON, ответ — в лог, для частых
команд есть подсказки. Подключение —
`localhost:25566`. Боты по умолчанию идут на него (`bot.port` 25566).
Python управляет им по RCON (`py/training_server.py`, `py/rcon.py`):
правила игры, арена 64x64 с препятствиями (`py/arena.py`), табло
«Мотивация» (награда каждого бота за 5 минут) и «Очки салок», роли и
свечение в салках, разброс по арене в начале раунда. Подробно — в
`server/README.md`. Если сервер-арена не отвечает, всё работает как раньше
на любом сервере (`bot.port` — поменять на его порт).

Тестовый рой рядом с рабочим: переменная `MCBOT_CONFIG` — путь к другому
config.json (свои порты ZMQ) для обеих сторон.

## Боты в плагине сервера (`plugin/`)

Вместо клиентов mineflayer (`js/`) ботами могут быть **настоящие игроки
сервера** из плагина Paper (`plugin/`, Java; идея автора, 2026-09-27):
физика и механика — ванильные серверные (скольжение вдоль стен, вода,
копание и постройка настоящие), нет отставания mineflayer от новых версий,
у ботов нет своих копий мира. Python (`py/ai_loop.py`) тот же: плагин
говорит с ним протоколом `js/bot.js` (состояния на `zmq.node_to_py`,
действия с `zmq.py_to_node`), состояние собирает теми же правилами (зрение,
сущности, слух, маршрут, удар — перенос `js/` один в один; сверено с
симуляцией на тестовом сервере).

Включается в `config.json`: `bot.body` — `"plugin"` (боты из плагина) или
`"mineflayer"` (как раньше, `js/bot.js`). С плагином лаунчер не запускает
Node: когда Python готов, шлёт серверу `/mcbot start` по RCON, на «Стоп» —
`/mcbot stop`, строка команд уходит как `/mcbot cmd <номер|all> <команда>`
(ответ Python — строкой `[cmd]` в его выводе). Имена ботов для людей —
`bot.names`: при входе каждому случайное, без повторов — «Егор [AI_1]» в
чате и списке игроков, «Егор» строкой под ником над головой (сам ник —
`AI_N`: на нём держатся команды сервера, салки и Python).

**Команды при запуске задачи** (с сервером-ареной): файл
`server/functions/<задача>.mcfunction` — команды сервера по одной на
строку (`#` — комментарий), выполняются по RCON, когда рой начинает эту
задачу (запуск с ней или `!task all <задача>`) и все `bot.count` ботов уже
зашли — иначе `@a` не застал бы ботов, — и снова в начале каждого круга
игры: каждая охота (`!start`, новая цель в `auto`) и каждый раунд салок
(`tag.mcfunction`): так инвентарь чистится и пополняется каждый раз, а не
только при первом `!task`. Пример — `server/functions/hunt.mcfunction`.

Собрать и положить в сервер (подхватит при следующем запуске сервера):

```
plugin\gradlew deploy
```

(Gradle 9.6, Java 25, paperweight-userdev — внутренности сервера под
именами Mojang; кеш Gradle — в `GRADLE_USER_HOME`.) Если плагин уже стоит,
новый jar ложится в `server/plugins/update` — Paper сам подменит его при
следующем запуске (перезапись jar у работающего сервера уронила бы плагин).
Команды оператора:
`/mcbot start [сколько]`, `/mcbot stop`, `/mcbot cmd ...`, `/mcbot list`,
`/mcbot walk <бот> [тиков] [sprint] [jump] [debug]` (пробная ходьба),
`/mcbot state <бот>` (состояние бота в файл — сверка с симуляцией),
`/mcbot goto <задачка|main> [ник]` (перейти в мир задачки и обратно).

**Миры задачек** (`config.json → bot.task_worlds`, сейчас `{"bridge":
"mcbot_bridge"}`): плагин при запуске сам создаёт их пустыми (своим
генератором пустоты — стороннего плагина миров не нужно), обычный мир под
задачки не перестраивается. Что в мире задачки строить и кого куда ставить,
решает Python — командами `execute in minecraft:<мир> run ...` по RCON.

## Запуск

```
run_ai_bot.bat
```

Открывает **одно окно-лаунчер** (`py/launcher.py`, tkinter — ставить ничего
не нужно): выбор задачи, «Старт»/«Стоп», общий лог Python и Node (строки
помечены `[PY]`/`[JS]`, каждый источник можно скрыть галочкой, ошибки
красным), строка команд и **«как дела» у каждой задачки человеческими
словами** — например, «looking (7 бот.): цель в прицеле 23% времени ↑ ·
случайных действий 40%» (стрелка — лучше/хуже прошлых замеров) — плюс
график главной цифры каждой задачки (выше — лучше).
Лаунчер сам запускает сначала Python, ждёт, пока тот забиндит порты, и
только потом Node. «Стоп» останавливает аккуратно — Python сохраняет
чекпоинты. Галочка «Перезапускать при падении» поднимает упавший процесс
заново — для долгого обучения без присмотра. То же самое: `npm run ui`.

Старый вариант с двумя консолями — `run_ai_bot_consoles.bat`. Или вручную,
в двух терминалах (сначала Python!):

```
python py/ai_loop.py --task walking
node js/bot.js
```

Для долгого обучения Node сам переподключает ботов, если сервер их
кикнул или перезапустился (пауза 5 с), остальные боты роя при этом
продолжают работать.

## Наблюдение бота

- **Зрение** (`js/vision.js`) — сетка raycast-лучей, режим задаётся
  `vision.mode`:
  - `circular` (по умолчанию) — круговое зрение: горизонталь всегда 360°
    (колонка 0 = прямо перед ботом, кольцо поворачивается вместе с ним),
    вертикально — `vision.vertical_fov` вокруг горизонта. Прицел (куда
    смотрит голова) при этом отдельная вещь — он нужен только для
    взаимодействия (`attack_center`), а не чтобы «увидеть».
  - `camera` — классическая сетка внутри FOV вокруг направления взгляда.
  Ряд 0 сетки — верх, последний — низ (как пиксели экрана).
  **Проверка зрения без сервера: `npm run test-vision`** — синтетический
  мир с известными блоками. (До 2026-09-24 зрение было сломано: raycast
  prismarine-world возвращает сам блок, а код читал `hit.block` — все лучи
  были «небом», `center_block` всегда `null`, `attack_center` не копал.
  Записи геймплея тех времён пропускаются автоматически.)
  Каждый луч: средний цвет блока (приблизительная палитра по имени) +
  нормированная дистанция + **класс блока** (`vision.block_classes`
  категорий: воздух, древесина, камень, земля, растения, жидкость, руда,
  снег/лёд, стекло, прочее — Python one-hot'ит их в каналы). Без
  «рентгена»: луч останавливается на первом попадании, но **проходимая
  растительность (трава, цветы, посевы, факелы и т.п.) лучами
  пропускается** — иначе цветок выглядел бы как стена вплотную.
- **Сущности** (`js/entities.js`) — `entities.max_tracked` сущностей в
  радиусе `entities.radius`, живые (игроки, мобы) первыми, потом неживое,
  внутри — ближайшие; каждая: положение в локальной системе взгляда
  (вперёд/вправо/вверх, нормировано), дистанция и класс (враждебная /
  мирная / игрок / неживое — выпавший предмет, стрела, шар опыта). Мобы и
  игроки видны на 360°. Класс берётся из категории minecraft-data, а она в
  новых версиях другая (`hostile`, `animal`, `other`...): до 2026-09-26 на
  26.1 зомби и выпавшие предметы считались «мирными мобами» (follow мог
  пойти за зомби, gathering не видел выпавших брёвен). Проверка — в
  `npm run test-vision`.
- **Граница мира** (`js/border.js`) — Node читает пакеты границы из
  сервера и кладёт её в состояние (`world_border`: центр и размер, только
  для модулей, не для сети): walking выбирает цели-точки внутри настоящей
  границы с отступом `modules.walking.border_target_margin`, а ручной
  `modules.walking.bounds` остаётся запасным вариантом, если сервер границу
  не прислал. Пакеты границы в разных версиях Minecraft называются
  по-разному — `border.js` понимает и новые (`initialize_world_border`,
  поля `x`, `z`, `newDiameter`), и старые; когда бот узнаёт границу, в
  логе появляется «граница мира — центр (…), размер N». До 2026-09-26 был
  ещё охранник (секция `world_border` в конфиге: бота у края
  разворачивало к центру, действие ИИ игнорировалось) — автор убрал: на
  сервере-арене по краю стена из барьера, а за границей мира сервер сам
  не пускает и наносит урон.
- **Слух** (`js/hearing.js`) — низкоприоритетный круговой сенсор: звуковые
  события Minecraft кладут затухающий заряд в один из 8 секторов вокруг
  бота (сектор 0 = перед ботом).
- **Память о движении** (`js/state.js`, `py/state_encoder.py`) — сеть по
  одному кадру не отличает «я иду» от «мир крутится», поэтому наблюдение
  дополнено: (а) дельты прошлого тика — сдвиг в локальной системе взгляда
  (`move_forward/move_right/move_up`, `dyaw/dpitch`): по ним видно, реально
  ли бот сдвинулся и не упёрся ли в стену; (б) стек последних
  `memory.frame_stack` кадров зрения — движение видно «глазами».
- **Цель** — только относительно бота: есть ли она, насколько довернуть
  взгляд (по горизонтали — sin/cos угла, по вертикали — доля от 90°),
  где она относительно тела (впереди/справа/выше) и дистанция.
  **Абсолютного поворота бота (куда он смотрит — на север или на юг) сеть
  не получает**: вживую с ним looking выучил «смотри на юго-запад» вместо
  «смотри на цель» и переставал работать, стоило ботам сдвинуться.
  Игрока-цель, которого сервер перестал присылать (дальше ~35 блоков),
  бот помнит 30 секунд — смотрит/идёт туда, где видел его последний раз.
- **Маршрут к цели** (`js/route.js`, секция `route` в конфиге) — A* по
  блокам: ходить можно по твёрдому, подниматься на 1 блок, спускаться до
  `route.max_drop` (3), вода, лава и прочее опасное — стены. В состояние
  уходит `route = {waypoint, length, complete}`: ближайшая точка маршрута
  (на `lookahead` клеток вперёд), длина пути и дошёл ли маршрут до самой
  цели (если цель недостижима — путь к ближайшей к ней клетке). Маршрут
  пересчитывается, когда цель сдвинулась, бот сошёл с пути или прошло
  `replan_ticks` тиков. Сети ходьбы (walking/follow/chase) показывают
  **точку маршрута вместо самой цели** (`observe` модуля), а награда за
  прогресс считается **по длине маршрута**, а не по прямой — обход стены
  или оврага больше не наказывается. Тест без сервера: `npm run test-route`.
- **Прицел** — что строго по центру взгляда: класс блока (как в сетке
  зрения), дистанция до него и достаёт ли рука (12 чисел). Круговая сетка
  зрения за наклоном головы не следует, и без этого бот, глядя вниз на
  блок, не «видел», во что целится: наводиться, чтобы копать и ставить,
  учился вслепую. looking прицела не видит (по нему можно заучить место).
- **Инвентарь** (`js/inventory.js`) — сводка из 8 чисел: сколько блоков
  (есть ли чем строить), еды, брони в инвентаре, сколько брони надето и
  что в руке (блок / еда / инструмент / другое).
- **Чувство пола** (`state.ground`, `js/vision.js: groundProbe`; в плагине
  `Vision.groundProbe`, в симуляции `sim/vision.ground_probe`) — сколько
  пола до края впереди, справа, сзади и слева (относительно взгляда), до 3
  блоков, со знаком: над пустотой (свесился с края) — минус, сколько до
  пола. Пол — блок со столкновением на уровне под ногами (шаг вниз — уже
  край). Сетка зрения смотрит вниз самое большее на 35° и край ближе ~2.3
  блока не видит, прицел — одна точка: без этого входа мост строили
  крадучись от самого старта. looking этот вход не видит (рельеф вокруг
  неподвижного бота выдаёт поворот).
- **«Блок встанет»** (`state.can_place`, `js/actions.js: canPlaceFront`; в
  плагине `Actions.canPlaceFront`, в симуляции `sim/game.free_for_block`) —
  1, если `place_front` прямо сейчас поставил бы блок: есть чем, грань в
  прицеле в досягаемости, клетка за ней — воздух и никто в ней не стоит
  (размеры тел — как у сервера, float). Как `strike` для удара. У края моста
  окно для блока узкое (свес 0.2857–0.3), и без этого входа сеть не
  отличала «в окне» от «замерла чуть раньше».
- **Прочее** — блок в центре прицела (`center_block`), health, food,
  `inventory_count`, наклон головы, признак «цель поставлена человеком».

## Пространство действий: каналы

Действия разбиты на три **канала** — у каждого своя сеть, и за тик каждая
выбирает своё действие; Node выполняет все три одновременно (идти +
смотреть + бить). Контракт — `CHANNELS` в `js/actions.js` и `py/protocol.py`.

| Канал   | Действия | Что это |
|---------|----------|---------|
| `legs`  | `idle`, `walk_forward`, `sprint_forward`, `walk_back`, `strafe_left`, `strafe_right`, `jump_forward`, `turn_left`, `turn_right`, `jump`, `sneak_back`, `sneak`, `turn_around`, `sneak_forward` | перемещение и поворот корпуса (30°; `turn_around` — сразу на 180°) |
| `head`  | `head_idle`, `look_up`, `look_down`, `look_left`, `look_right` | только взгляд: наклон и доворот по 10° |
| `hands` | `hands_idle`, `attack_center`, `place_below`, `place_front`, `use_item`, `equip_armor`, `drop_item` | взаимодействие с миром и инвентарём |

**Новые действия дописываются только в конец** своего канала (и в
`ACTION_NAMES` в `py/protocol.py` — там явный список, он тоже только
дописывается): номер действия = номер выхода сети. Тогда уже обученные
мозги не выбрасываются, а **доращиваются** (`_grow_state_dict` в
`py/dqn.py`): новый выход получает заниженную оценку (сеть не выберет его,
пока не распробует), старые выходы не меняются вовсе — проверено на
настоящих мозгах follow и looking: тот же выбор в 200 из 200 ситуаций.
Так же с входами: новые — в конец `scalar_layout`, их веса в первом слое
нулевые, и на старых данных сеть считает ровно то же, что раньше. В логе
при загрузке: «доращён без потери навыков (legs: входов 122 -> 136,
действий 9 -> 10)».

Зачем разделять: раньше одна сеть выбирала одно действие на всё, и
walking, у которого по смыслу только ноги, мог выбирать `look_up`/
`look_down` — отсюда «бесцельное верчение головой». Теперь у сети ног
этих действий просто нет, а сеть головы отдельно учится не вертеться,
когда задача этого не требует (штраф `head_move_penalty` в walking).

**Голова поворачивается у всех на глазах сразу.** mineflayer сам
показывает серверу поворот головы плавно (не быстрее 172° в секунду), а
прицел у бота меняется мгновенно (30° ногами, 10° головой за тик) — видимая
голова отставала, и казалось, что бот ломает не там, куда смотрит. Теперь
любой поворот уходит серверу сразу (`ActionExecutor.turnView`), а при
копке и ударе голова доворачивается на цель, при «поставить под себя» —
смотрит вниз, как игрок, строящий столб.

В Minecraft у игрока один yaw и на взгляд, и на направление ходьбы
(физика mineflayer двигает бота по `entity.yaw`), поэтому `look_left`/
`look_right` головы тоже чуть поворачивают курс — они просто мельче и
нужны для точного наведения.

**Как сети «общаются».** Каждая сеть видит на входе, кроме наблюдения,
**контекст** (`state_encoder.encode_context`): one-hot активной задачи и
что делали ВСЕ каналы на прошлом тике. Голова видит, что ноги сейчас
поворачивают, руки — что голова навелась. Сети решают одновременно,
поэтому «соседи» — это их решения 150 мс назад.

`jump_forward` — готовая комбинация «прыжок + вперёд» за один вызов, чтобы
сеть не подбирала клавиши по отдельности. `walk_forward` и `sprint_forward`
сами подпрыгивают на уступ высотой в блок, над которым свободно, — как
«автопрыжок» в настройках игры (`ActionExecutor.stepAhead`, тест —
`npm run test-actions`). Без этого боты упирались в уступ и «шли» на месте:
лучи зрения идут от глаз и проходят над таким уступом, сеть его почти не
видит. Стену в два блока не перепрыгнуть — её обходят. `sprint_forward` — то же
движение, что и `walk_forward`, плюс control state `sprint` (сервер сам не
даст бежать при низкой сытости — бот просто пойдёт шагом, без ошибок).
`attack_center` (gathering, удар в салках) — бьёт ближайшую подходящую
сущность перед ботом: до 3.5 блока, не дальше ~30° влево-вправо от
взгляда, по высоте — любую (голову удар наводит сам; до 2026-09-26 конус
считался с наклоном взгляда, и водящие не попадали по убегающему ближе 2
блоков). Если такой нет — копает блок строго по центру прицела. Копка идёт, **только пока блок в прицеле и ближе 4.5 блока**:
отвернулся или отошёл — прерывается, как в игре (сам mineflayer, начав,
докапывал блок, куда бы бот ни ушёл, — и боты ломали блоки издалека).

`jump` — прыжок на месте. `sneak_back` — задом крадучись, `sneak` — стоять
крадучись: крадущегося игра с края блока не пускает (так строят мост над
пустотой) и он втрое медленнее. Боту шифт нужнее, чем человеку: решение
раз в 150 мс, клавиши держатся 250 мс — без шифта у края он срывался бы.
Отпустить шифт у края, пока давишь назад, — сорвёшься (как игрок), поэтому
шифт "липкий": когда удержание клавиш истекает (ответ Python запоздал),
движение отпускается, а шифт держится до следующего решения. В плагине
замедление крадучись делает сам бот (у игрока его делает клиент игры,
серверу приходит уже медленный шаг). Руки (всё — макросы в `js/actions.js`, долгие
дела рук не накладываются друг на друга и сами отпускаются по таймауту):
- `place_below` — поставить блок из инвентаря под себя. Получается только
  в прыжке (клетка под ногами должна освободиться), поэтому макрос на земле
  подпрыгивает сам (и снова — если приземлился, не успев поставить), ждёт,
  пока ноги поднимутся выше клетки (до 0.5 с), и бот встаёт на блок выше.
  Так строится столб — одним этим действием рук: раньше нужен был ещё `jump`
  ногами в тот же тик, и две сети (ноги и руки) этому так и не научились;
- `place_front` — поставить блок на грань того, во что смотрит прицел
  (стена, мост, ступенька);
- `use_item` — голоден и есть еда — поесть, иначе «использовать» предмет в
  руке;
- `equip_armor` — надеть первую подходящую броню из инвентаря;
- `drop_item` — выбросить то, что в руке.

Сытость (`self.food`, источник — `bot.food`, а не `entity`) в состоянии
есть у всех модулей, но осмысленно её использует пока только факт «может
ли бот сейчас спринтовать» — отдельного штрафа за голод в наградах нет.

## Обучающие модули (специализации)

DQN сам по себе не знает, «за что» давать награду — это решает подключаемый
**обучающий модуль** — он же **задача** бота (`py/training_modules/`).
Модуль умеет две вещи: расставлять/менять цель бота (`on_tick`, если это
вообще нужно этой специализации) и считать награды за прошлый переход под
эту цель (`compute_reward`) — **отдельно для каждого канала**. Основа
обычно общая, командная («дошли до точки — молодцы все»), плюс точечный
шейпинг конкретному каналу (голове — штраф за верчение без дела, рукам —
за удар в воздух). Ядро (`ai_loop.py`) про конкретные награды ничего не
знает — просто дёргает эти методы каждый тик.

**У каждой задачки свой мозг** (сети каналов + память опыта + своё
расписание случайных действий), чекпоинты — `data/brains/<задачка>/<канал>.pt`.
Раньше мозг был общим, и когда боты переключались на другую задачку, её
обучение затирало навыки прежней («катастрофическое забывание»: looking
после смены задачи и возврата «отупевал»). Теперь переключение ничего не
затирает — вернулся к задачке, и она продолжает с того же места. Чтобы
не учить ходьбу с нуля в каждой задачке, новый мозг follow и gathering
стартует с весов мозга walking (`train.warm_start_from`), если тот уже
обучен. Канал, которому задачка разрешает ровно одно действие (руки в
looking), сети не получает — выбирать не из чего.

Задача по умолчанию — флагом при запуске (или выпадающим списком в
лаунчере), на лету — из чата, причём у разных ботов роя могут быть разные
задачи одновременно:
```
python py/ai_loop.py --task mix          # разные задачки разным ботам (рекомендуется, по умолчанию в лаунчере)
python py/ai_loop.py --task tag          # салки: один водит, остальные убегают
python py/ai_loop.py --task walking      # по умолчанию в консоли (старое имя флага --module тоже работает)
python py/ai_loop.py --task looking
python py/ai_loop.py --task follow
python py/ai_loop.py --task gathering
python py/ai_loop.py --task crafting     # пока заглушка, см. TODO в файле

!task gathering        — в чате: сменить задачу (общий чат слышат все боты, одному — /msg AI_3 ...)
!task all mix          — всему рою
```

**Разрешённые действия.** Каждая задачка объявляет, какие действия
каналов ей разрешены (`allowed_actions` в модуле), остальные сеть в этой
задаче не выберет вообще — ни жадно, ни случайно (маска в `py/dqn.py`,
и в TD-цели тоже). Первые часы почти все действия случайные, и без маски
в «следить взглядом» боты ходили бы и ломали блоки. Сейчас: walking и
follow — голове только наклон, руки выключены; looking — ногам только
стоять/поворачиваться, руки выключены; gathering — рукам только
бить/копать; chase и flee (салки) — полная свобода.

**Задачки** — короткие задания с понятным «получилось/нет»: частая
награда учит быстрее одной большой задачи. **Режим `mix`**: боты роя
стартуют с разных задачек из `train.mix_tasks` (бот 1 — walking, бот 2 —
looking, бот 3 — follow, бот 4 — gathering, бот 5 — снова walking…) и
каждые `train.mix_rotate_ticks` тиков переходят к следующей. Сети общие,
так что за один прогон учатся все навыки сразу и на разной местности.

**Режим `tag` — салки-«заражение»** (идеи автора). Один бот **водит**
(задачка `chase`) — догоняет остальных, остальные **убегают** (`flee`); у
ролей свои мозги. Правила ведёт судья `py/tag_game.py` (`modules.tag` в
конфиге):
- раунд начинается с одного случайного водящего: он `freeze_seconds` (5 с)
  стоит — «считает до пяти», — остальные разбегаются. Убегающий бежит от
  ближайшего водящего;
- осалить = догнать и **ударить** (`attack_center`), стоя ближе
  `tag_distance` (4 блока). Бить игроков можно только водящему и только
  убегающих: список id убегающих Python присылает ему с каждым действием
  (`tag_ids`). Кого ударил, Node сообщает в состоянии (`attacked_id`);
- осаленный **тоже водит** (водящий водит дальше) и тоже сначала считает
  до пяти. Водящий пишет в чат: «Я догнал AI_3. Теперь и он водит!».
  Сколько водящих — не настройка: сколько осалили, столько и водят;
- осалили последнего — «Ура, все молодцы, ещё раз!»: водящим награда,
  пауза 3 с (все стоят, опыта нет), всех разбрасывает по арене
  (`/spreadplayers` — телепорт, а не смерть, наказывать не за что; только
  на нашем сервере-арене) и снова водит один случайный;
- раунд идёт дольше `round_seconds` (5 минут) — «Время вышло! Не
  поймали: …» — непойманным награда, дальше так же: пауза, разброс,
  новый раунд. Водящие ушли из игры — водит случайный убегающий;
- только что возродившийся `respawn_seconds` (3 с) не салит и не салится:
  все возрождаются в одной точке, и вживую умершие «ловили» друг друга
  прямо там;
- водящий бежит за ближайшим убегающим и не мечется между двумя почти
  равными (`switch_margin`);
- застоялся — `idle_seconds` (45 с) не отходил дальше `idle_radius`
  (2 блока): штраф `idle_penalty`, и судья делает ему `/kill` (`kill_idle`)
  — автор так наказывал стоящих ботов вручную. Без этого убегающие, пока
  водящий неумелый, выучивали «стоять выгоднее всего»: награда за «не
  осалили» капала и стоя. Смерть — сильный сигнал «так не надо», а заодно
  бот выбирается из ямы.

**Играть с ботами можно и самому** — и убегать, и водить. Роли — команды
сервера: `it` (водящие, красные, с приставкой `[водит]`) и `runners`
(убегающие, белые). Войти в игру — `/team join runners <ник>` (или
`/team join it <ник>` — сразу водить), выйти — `/team leave <ник>`. Люди
играют, только пока они в выживании или приключении: в наблюдателе и
творческом режиме водящие их не трогают. Осалил бот человека — человек
переходит в `it` и тоже «считает до пяти» (замедление 255 на 5 с); осалил
человек-водящий бота — бот водит (удар человека судья видит по урону у
бота: `hurt_by` в состоянии, поэтому на сервере должно быть включено PvP —
сервер-арена включает правило `pvp` сам). Где люди и в какой они команде,
судья знает от ботов (`state.humans`: ник, id, позиция, режим игры,
команда). Свои своих не бьют (`friendlyFire false` у обеих команд).

**Кто водит — видно в игре.** На нашем сервере-арене судья помечает роли
командами по RCON: цвет ника по команде и свечение сквозь стены
(`/effect glowing`) — бота видно, даже если он ушёл в пещеру. Смерть
снимает эффекты — после респавна свечение выдаётся заново (`mark_roles`).
На чужом сервере команды идут от имени бота №1 (`command_bot`, ему нужен
op: `/op AI_1`) очередью, не чаще раза в `command_interval` (1.1 с): сервер
кикает за флуд всех, кроме op, — так бот без op не вылетит, просто пометки
не будет. Сменить боту ник на лету нельзя: ник задаётся при входе.

Исходы — конец эпизода: осалил — водящему `tag_reward` (50), осалили —
убегающему `caught_penalty` (−50), поймали всех — каждому водящему
`modules.chase.round_reward` (20), время вышло, а тебя не поймали —
`modules.flee.survivor_reward` (20). Время вышло у водящего — не конец, а
обрыв эпизода: время раунда сети не видно. Водящий учится как в walking:
маршрут к убегающему, награда за каждый блок ближе по маршруту, давление
времени до самого удара (подбежать мало — надо ударить; чем быстрее
поймали — тем меньше набежало минусов). Убегающим — «эйфория»:
`survive_reward` за каждый тик, пока не осалили (чем дольше не салят, тем
больше набрано), плюс `distance_reward` за расстояние до водящего, плюс
«дразнить воду» (идея автора; «вода» — водящий): `tease_reward` больше
всего в `tease_peak` (6) блоках от водящего — чуть дальше, чем он салит, —
и сходит на нет за `tease_width` (4) блока в обе стороны. Подойди
поближе, но не попадись: в 6 блоках награда +0.81 за тик, вдали +0.5,
вплотную +0.24, а осалят — −50. Где кто,
судья знает из состояний самих ботов, поэтому цель не теряется, даже когда
сервер её боту не показывает (далеко). В лог: «Салки: AI_4 осалил AI_2 —
убегающих осталось 5».

Правила салок уже менялись: до 2026-09-26 было наоборот — один убегал, все
догоняли, поймать = подбежать. Под новыми правилами у мозга водящего
`modules.chase.version` = 2: мозг, обученный под старыми, загружается с
навыками (бег к цели), но случайные действия у него начинаются заново —
иначе он так и не попробовал бы ударить (в старой игре удар был
бесполезен). Так же можно поступить с любой задачкой, если поменялись её
правила.

**Задачка `bridge` — мост над пустотой** (первый шаг к бедварсу): у каждого
бота своя дорожка (`py/bridge_course.py`, через 20 блоков по x) — остров
старта и остров цели, внизу пустота. Каждая попытка — своя раскладка и свой
вид моста (у ботов роя в каждый момент разные): **прямо** (пропасть 3–12,
остров цели сдвинут вбок до 2), **вверх** (остров цели выше на 1–2 —
сначала столб `place_below`), **вниз** (ниже на 1–3 — мост до края над ним
и шаг вниз; засчитано, только когда стоит на острове), **«Г»** (остров в
стороне на 5–7 блоков — вперёд до его ряда, поворот, вбок); старт — в
разных местах острова. Строят так: спиной по оси моста, взгляд вниз -80°,
задом обычным шагом, пока сзади хватает пола (чувство пола), у края —
крадучись (`sneak_back`), и `place_front` — луч из-за края попадает в бок
блока под ногами. Свес у края, при котором блок встаёт, узкий (0.2857–0.3
блока), а крадущегося игра отодвигает шагами по 0.05 — бывает, бот замирает
чуть раньше окна; тогда шаг вперёд и заход заново (так делает учитель).
Судья (`ai_loop._bridge_turn`) ставит цель, засчитывает «дошёл»
(`cross_reward` и бонус за скорость: `speed_bonus` за мгновенный переход,
половина — за норму `par_extra + par_per_block * длина пути`, ноль — за две
нормы) и «упал» (`death_penalty`, бота сразу возвращает на старт — до смерти
в пустоте), перед каждой попыткой чистит дорожку, строит острова новой
раскладки, выдаёт блоки (`start_blocks`) и ставит бота на старт лицом в
случайную сторону (кратно 10° — чтобы можно было встать ровно). Застрял
дольше max(`attempt_seconds`, две нормы) — новая попытка. В сводке — сколько
переходов, среднее время и «дошёл из попыток» по видам моста. В игре — только в мире задачки
(плагин, `bot.task_worlds.bridge`): без него судья мост не строит, обычный
мир не трогает. `!task all bridge`; посмотреть — `/mcbot goto bridge`.
Случайных действий у моста меньше обычного (`modules.bridge.epsilon_end`
0.01: у края случайный шаг без шифта — падение); у любой задачки можно
задать свой `epsilon_end`.
Мосту не нужны и выключены входы слуха, сущностей, удара, заряда удара,
маршрута и «ближайшего» (`modules.bridge.inputs`): вживую они другие, чем в
симуляции (плагин всегда строит маршрут — через пустоту его нет; заряд
сбрасывается после каждого блока; рядом может стоять зритель), и сеть от них
вживую строила лишние столбы. Судья при старте вычищает весь мир трассы от
старых построек, а перед попыткой — дорожку до +48 над островами: чужие
высокие столбы сеть видела и лезла строить сама.
Учить в симуляции: `python py/train_tag_sim.py --game bridge --teachers 4
--rescue` (учитель — `sim/teacher.bridge_actions`; `--rescue` — учитель ещё
и подсказывает остальным ботам в их же ошибке: замер у края чуть раньше
окна — шаг вперёд, это пример для мозга; проверять — без учителей и без
`--rescue`).

**Задачка `bedwars` — бедварс ботов** на картах Hypixel (17 карт автора в
`server/bw_maps/`, миры 1.8). Судья — `py/bedwars_game.py`: случайная карта,
рой делится на матчи по две команды (`modules.bedwars.team_size` игроков в
команде, по умолчанию 2: 4 на 4 на одном мосту шли вничью) — каждый матч на
своей паре соседних островов одной стороны карты (мост прямой); команды
сервера (`/team`) — цветом острова. Набор — деревянный меч; шерсть своего
цвета — за железо: у точки появления генератор (железо и золото копятся,
забирает тот, у кого железа меньше), действие рук `buy` там же — 16 шерсти
за 4 железа (магазин без меню). В команде из двух и больше первый — иногда
(`defend_chance`) защитник: закрывает кровать шерстью и стоит у неё. Кровать цела —
умерший через 5 с возрождается у себя; сломана — выбывает (зритель); упал в
пустоту — умер; ломать можно только поставленные блоки и кровати; победа в
матче — выбыли все соперники; все матчи кончились или время вышло (ничья) —
новая игра. Боту судья говорит,
куда идти (враг рядом — он, иначе чужая кровать) и кого можно бить
(соперников). Награды — за сломанную кровать, убийство, удары, победу;
штраф — за смерть и свою кровать (`modules.bedwars`).
Карты: `python py/bedwars_maps.py` — описания `data/bedwars/maps/<карта>.json`
(кровати, точки появления, генераторы, найденные по раскладке островов;
поправить руками можно, `"manual": true`); `--convert` — сетки блоков для
симуляции (переводит сам сервер: нужен запущенный сервер с плагином);
`--shapes` — формы блоков из Node. На сервере карта ставится и сбрасывается
командой `/mcbot bedwars <карта>` (мир задачки `bot.task_worlds.bedwars`
перезагружается из регионов карты; Paper сам переводит чанки 1.8). Играть:
`!task all bedwars` (нужен плагин и мир задачки), посмотреть — `/mcbot goto
bedwars`. Учить в симуляции: `python py/train_tag_sim.py --game bedwars --bots 8
--teachers 4` (учитель — `sim/teacher.bedwars_actions`; вживую учитель по
умолчанию ведёт всех ботов бедварса — `modules.bedwars.live_teachers`, пока
мозг не выучится); симуляция на картах
совпадает с игрой (формы блоков, ступени, лёд, лестницы — сверка
`python py/sim/check_bedwars_parity.py --all`).

**Упражнения бедварса** (`py/bedwars_drills.py`; автор: "сначала нужно
оттачивать механики"). Судья вперемешку с играми даёт упражнения — веса
`modules.bedwars.scenarios` (`game`/`duel`/`edge`/`dig`/`mini`;
в config.json игра/дуэли/край/прокопаться/мини — 1/2/1/1/2), упражнение
длится `drill_seconds`:
  - **дуэли** 1 на 1 над пустотой — мост в 1–3 блока или островок, у обоих
    деревянный меч; упал или убит — проиграл (`duel_win_reward` победителю),
    через секунду реванш на новой площадке, дольше `duel_seconds` — ничья;
  - **ходьба по краю** — тропа над пустотой (повороты, уступы вверх и вниз,
    ширина 1–3) от пятачка старта до пятачка цели: дошёл — `goal_reward` и
    новая тропа, упал — смерть и новая тропа, дольше `edge_seconds` — новая;
  - **прокопаться к кровати** — на островке кровать под куполом из 1–2 слоёв
    (шерсть, доски; укрытие помечено "поставлено игроком" — `/mcbot placed`):
    сломал кровать — `goal_reward` и новый островок, дольше `dig_seconds` —
    новый;
  - **мини-бедварс 1 на 1** — два островка с кроватями через пропасть 5–10
    блоков, у обоих меч и `mini_blocks` шерсти: мост навстречу врагу, драка,
    кровать; как игра (победа — `win_reward`), возрождение через
    `mini_respawn_seconds`, потом реванш, дольше `mini_seconds` — ничья.
Упражнения идут в своём мире `bot.task_worlds.drills` (плагин создаёт его
пустым и не перезагружает; `/mcbot drill x0 z0 x1 z1` — загрузить участок
дорожек), дорожки строит судья командами fill. Учитель (`sim/teacher.py`):
в дуэли бьёт только полным зарядом, разворачивается сразу (`turn_around`),
пока заряд копится — отступает; на тропе идёт от клетки к клетке маршрута
(`state.route.next`), у края и по тропе в блок — крадучись (`sneak_forward`:
вживую ответ доходит с опозданием, а крадущийся с края не сорвётся).

**Задачка `hunt` — «Останови меня»** (идея автора): боты догоняют цель и
бьют, пока не остановят. `!task all hunt`, приготовься и напиши `!start`
(или `!start <ник>` — охота на другого игрока, из лаунчера тоже). Цель
может быть и ботом роя: `!start AI_3` — он убегает своим мозгом
убегающего (flee), остальные ловят; `!start auto` — цель каждый раз
случайный бот, и после "остановки" охота начинается заново сама
(`modules.hunt.restart_pause_seconds`), — боты тренируются друг на друге
без тебя; не остановили цель за `modules.hunt.auto_seconds` (90 с) — новая
цель. Бот-цель может отбиваться: бить Node/плагин ему дают охотников
(награда убегающему — `modules.flee.hit_back_reward` за урон). Смерть
охотника — штраф `modules.hunt.death_penalty` (-20, а не общие -100: цель с
мечом убивает охотников часто, и с -100 им было выгоднее не подходить). Через
`modules.hunt.head_start_seconds` (3 с) боты срываются; бьют только цель.
Награда — как у водящего в салках (маршрут, давление времени) плюс
`hit_reward` за каждый удар, нанёсший цели урон, — с учётом силы удара, как
урон в игре (0.2 + 0.8 · заряд²: кулак "перезаряжается" 0.25 с; сеть видит
заряд — вход `charge`), и `kill_reward` всем охотникам, когда цель умерла
(по сообщению сервера о смерти). Махать каждый тик невыгодно: взмах
сбрасывает заряд, а удар в полсекунды неуязвимости после урона не наносит
ничего. После этого боты стоят до
следующего `!start`. Руки — только удар; новый мозг начинает с навыков
водящего (`train.warm_start_from`: hunt ← chase). Играть надо в выживании —
в творческом бить можно, но "остановить" нельзя. В мирной сложности
здоровье восстанавливается на 1 в секунду, а после урона полсекунды
неуязвимости: добить можно только плотной атакой (в симуляции — ~42 удара
в минуту по цели, идущей шагом, и то не хватало).

**Симуляция салок** (`py/sim/`, `py/train_tag_sim.py`). Та же арена, та же
физика (перенос prismarine-physics), то же зрение и маршруты (перенос
js/vision.js и js/route.js), а учит тот же ai_loop с тем же судьёй и
наградами — без Minecraft. Совпадение с игрой проверено числами
(`python py/sim/check_parity.py`: зрение, прицел, маршруты и траектории
движения — бит в бит). Учить: `python py/train_tag_sim.py --minutes 30`
(мозги — в `data/sim/brains/`, игровые не трогаются), перенести в игру —
`--install` при остановленном рое (`--install chase flee` — только эти,
старые игровые откладываются в `data/brains_old/`). Замер 2026-09-26: узкое место — не
Minecraft, а шаг обучения на видеокарте (~40 мс; при живом рое рядом —
~110 мс): симуляция упирается в него так же, как игра, так что ускорения
"в разы" она не даёт, пока шаг обучения не станет дешевле. Зато в ней есть
**учитель** (`py/sim/teacher.py`, `--teachers N`): простые правила
(водящий — к точке маршрута и бить, когда удар достаёт; убегающий — туда,
где свободно и дальше от водящего) ведут N ботов, и их ходы уходят мозгам
как примеры (демо-память, DQfD). Проверка без обучения — `--eval`: сколько
осаливаний в минуту игры (учителя между собой — ~14, мозги до учителя — ~1.4).
Охота в симуляции: `--game hunt` — на случайного бота по кругу (как
`!start auto`), `--game hunt --scripted-target` — на "человека", которого
ведёт учитель убегающего (ходит шагом, `--target-sprint` — бегает; с
вероятностью `--pillar-chance` строит столб, `--box-chance` — закрывается
коробкой; прятаться начинает, когда охотник ближе `--hide-distance` блоков —
по умолчанию 48, то есть сразу: укрытие готово до подхода ботов, как вживую;
`--hunt-seconds` — предел охоты; у охотников случайный набор блоков и меча,
`--fixed-kit` — у всех полный). Учитель охотника бьёт мечом, как только удар
убивает, кулаком — только в полную силу, в падении — критом;
цель на столбе — лезет следом (ближайший) или копает под ней, в коробке —
вскрывает стену. В начале охоты всем — `modules.hunt.start_blocks` блоков и
меч с остротой `modules.hunt.sword_sharpness` (как `give @a` в
`server/functions/hunt.mcfunction`: меч в руке, блок — пока строит,
урон — как у меча в игре; 0 — кулаки). Поменял набор в hunt.mcfunction —
поменяй и эти два числа, иначе сеть в игре увидит в руке не то, чему
училась. `--snapshots <папка>` — копия мозгов при каждой сводке: лучший
мозг бывает посередине прогона, снимки проверяются через `--eval`.

Цель-сущность: модули looking и follow «цепляются» к сущности по id
(`current_target = {"entity_id": id}`), Node каждый тик сам берёт её
свежую позицию (`js/target.js`) и добавляет высоту (`target.h`), чтобы
смотреть в лицо, а не в ноги.

| Модуль      | Кто расставляет цель                          | За что награда |
|-------------|------------------------------------------------|----------------|
| `walking`   | сам модуль — случайные точки вокруг бота внутри границы мира | ногам (в walking/follow голова только наклоняется и на движение не влияет — ей лишь «держи взгляд ровно»): плотная награда за каждый блок приближения, за разворот к цели (`heading_reward`), `reach_goal` один раз при подходе и `near_goal_reward` за каждый тик рядом (важно для цели-игрока), штраф за топтание на месте (стоит и не поворачивается), реакция на препятствие по курсу (`turn_left`/`turn_right`/`jump_forward` ног рядом со стеной поощряются, `walk_forward`/`sprint_forward` в стену — штрафуются), штраф за потерю здоровья. Голове дополнительно: штраф за задранный/опущенный взгляд (`pitch_penalty`) и за любое движение без дела (`head_move_penalty`). Рукам: штраф за `attack_center` (`hands_penalty`). Прогресс меряется по маршруту в обход препятствий (`js/route.js`), и каждый тик в пути немного в минус (`time_penalty`) — поэтому бег (`sprint_forward`) окупается |
| `looking` — «следить взглядом» | человек через `!setTarget`, иначе модуль сам цепляется к ближайшей сущности (не к предмету) | за доворот к цели — `track_reward` за радиан, **каждому каналу за свой собственный поворот** (ноги крутят на 30°, голова на 10° — с общей наградой правильный доворот головы тонул в случайных поворотах ног). Всем: цель в поле зрения камеры — плюс, в прицеле (< `center_angle_deg`) — большой плюс за тик, загорожена блоком — без плюсов. Ногам — штраф за ходьбу. Своё у задачки: короткий горизонт (`gamma` 0.9 — «навестись» решается за секунду), смерть не штрафуется (убежать нельзя), мозг **не видит** зрения, сущностей и слуха (`inputs`) — иначе заучивал место вместо правила |
| `follow` — «следовать» | человек через `!setTarget player`, иначе: человек → мирный моб → бот роя с меньшим номером (без циклов «два бота идут друг за другом и стоят») | как walking, но цель — коридор [`min_distance`, `max_distance`] (2–5 блоков): дальше — награда за сближение и разворот к цели, в коридоре — `in_band_reward` за тик, вплотную — штраф. Своё: `gamma` 0.95 (награда за каждый шаг плотная), случайные действия уходят за 80k шагов (~30 мин). Прогресс — по маршруту в обход ям и стен (`js/route.js`), каждый тик вдали от цели немного в минус (`time_penalty`) — так окупается бег |
| `chase` — салки, «водить» | судья салок: ближайший убегающий | как walking: прогресс по маршруту к убегающему, `time_penalty` до самого удара; осаливание (удар вплотную) засчитывает судья — `tag_reward`. Награда общая на все каналы (ноги догоняют, голова наводится, руки бьют, а мост из блоков — тоже путь). Бить ботов роя может только водящий. Стартует с мозга follow |
| `flee` — салки, «убегать» | судья салок: водящий (сеть видит угрозу напрямую, без маршрута) | «эйфория»: `survive_reward` за тик, пока не осалили, + `distance_reward` за расстояние до водящего, осалили — `caught_penalty`. Общая на все каналы: убежать можно и ногами, и столбом |
| `gathering` — «добыча» | не расставляет, ресурс ищет глазами | норма: добыть `quota` (5) предметов `resource_items` (брёвна). Всем: `item_reward` за каждый, `quota_reward` за норму (и сразу новая), мелочь за прочие предметы, подсказки — сближение с блоком ресурса в сетке зрения (`resource_class`) и с выпавшим предметом (дроп надо подобрать). Голове — плюс, пока в прицеле ресурс в зоне удара; рукам — плюс за удар по нему, штраф за удар в воздух. Ресурс в сеть не подаётся — сеть учит тот, что в конфиге |
| `crafting`  | — (заглушка)                                    | 0, кроме штрафа за смерть |

**Чат-команды человека всегда главнее модуля.** Как только сказал
`!setTarget player <имя>` или `!setTarget position <x y z>` — эта цель
используется для награды и остаётся активной, пока не скажешь
`!setTarget none` (тогда управление целью возвращается модулю). Это
работает на стороне Node (`js/target.js`, `TargetManager`) — модуль вообще
не знает, откуда взялась итоговая цель, он просто видит её (или её
отсутствие) в `state["target"]`.

Чекпоинты — `data/brains/<задачка>/<канал>.pt`. Новые действия и входы,
дописанные в конец, доращивают сеть без потери навыков (см. «Пространство
действий»); если набор действий канала поменялся как-то иначе, заново
учится только этот канал. Warm start нового мозга:
мозг родственной задачки (`train.warm_start_from`), иначе
`data/bc_<канал>.pt` из behavior cloning. Старые общие `data/net_*.pt`,
`data/dqn_<module>.pt` и `data/bc_weights.pt` не читаются — цикл напишет
об этом при старте, их можно удалить.

**Как добавить свой модуль:** файл в `py/training_modules/`, класс
наследует `TrainingModule` (см. подробный докстринг в `base.py`),
регистрация в `MODULES` и в конец `TASK_ORDER` в
`training_modules/__init__.py` (номер задачи идёт на вход сетей — порядок
не менять), по желанию — секция параметров в `config.json → "modules" →
"<name>"`.

## Обучение

По сети на канал в мозге задачки: CNN над стеком кадров зрения + MLP над
скалярами (слух, углы sin/cos, health, дельты движения, сущности,
относительная цель, контекст задачи и прошлых действий) → dueling-голова
→ Q-значения по действиям своего канала. Поверх классического DQN:

- **Double DQN** (`train.double_dqn`) — действие для TD-цели выбирает
  онлайн-сеть, оценивает target-сеть: меньше систематической переоценки Q;
- **Dueling** — Q = V(s) + A(s,a) − среднее A: «ценность ситуации»
  учится по всем переходам сразу, стабильнее;
- **n-step возвраты** (`train.n_step`, 3) — награда за цель доходит до
  решений, принятых на несколько тиков раньше, за один проход обучения;
- **маска действий задачки** — и при выборе действия, и в TD-цели;
- **память опыта у каждой задачки своя**: переход хранит наблюдение один
  раз, а действия и награды — по каждому каналу. Зрение хранится
  компактно (uint8: 5 байт на луч), в полный вход сети его разворачивает
  `expand_vision` уже на видеокарте — переход ~2.5 КБ, 100k переходов
  ~250 МБ на задачку.

Случайные действия (epsilon) — у каждой задачки свои: линейно 1.0 → 0.05
за `train.epsilon_decay_steps` (150k шагов этой задачки ≈ 55 минут роем
из 7 ботов), у простой looking — быстрее (`modules.looking.epsilon_decay_steps`,
60k ≈ 22 минуты). Счётчик шагов — в чекпоинте, после перезапуска
продолжается с того же места.

**Бот действует по свежему кадру.** Node после отправки состояний ждёт
действия ИМЕННО на них (Python помечает ответ номером тика), до 60 мс;
обычно ответ приходит за ~8 мс. Раньше Node ждал 1 мс и почти всегда
выполнял действие, выбранное по прошлому кадру, — сеть видела результат
своего решения только через тик. Если Python не успевает, в логе Node
будет «ИИ не успевает отвечать».

**Отвечать и учиться — в разных потоках.** Боты получают ответы по
копиям сетей (`actor_net`), а обучаемые сети учатся в отдельном потоке
непрерывно, со своим CUDA-потоком, и каждые `train.actor_sync_every` шагов
обновляют копии. Раньше обучение шло урывками между тиками в том же потоке:
шаг ~50 мс задерживал ответы, и с 14 ботами опаздывали 44% ответов. Теперь
(замер на фейковом рое): 14 ботов — 1% опозданий, ~19 шагов обучения в
секунду по 512 переходов (было ~5 по 256). `train.learn_duty` (0.85) —
какую долю времени видеокарта учится: на ней же рисуется игра. Мозги на
диск пишет поток обучения, между шагами.

Темп обучения: каждое состояние добавляет мозгу своей задачки
`learn_steps_per_tick` (0.5) «кредита» обучения, а шаги обучения (батч
256, ~20 мс на шаг — время уходит на запуск CUDA-ядер, не на математику)
делаются ПО ОДНОМУ между ответами ботам, с проверкой сокета перед каждым:
отвечать ботам важнее, и бот никогда не ждёт дольше одного шага. Учиться
мозг начинает, только когда в памяти опыта `train.learn_start` (20000)
примеров: память при запуске пустая, и первые шаги по сотне примеров
портили обученный мозг (вживую мост падал вдвое чаще, чем без обучения).

**Метрики**: каждые `train.metrics_every_seconds` (30 с) по каждой задачке —
строка «как дела» от самого модуля (`TrainingModule.summarize`): looking —
«цель в прицеле N% времени», follow — «рядом с целью N% времени»,
walking — «дошёл до точки N раз», gathering — «добыто N», плюс смерти,
доля случайных действий, награда и loss. Всё это пишется в консоль, в
`data/metrics.csv` (строка на задачку за окно) и показывается в лаунчере.
Отчего умирают боты — видно в логе Node: «Причина смерти: AI_3 fell from a
high place» (из сообщений сервера).

**Автосохранение**: мозги пишутся каждые `train.autosave_ticks` состояний
и на смерти бота (не чаще раза в минуту) — падение процесса не теряет
прогресс, Ctrl+C и «Стоп» в лаунчере тоже сохраняют.

## Предобучение looking в симуляции

```
python py/pretrain_looking.py        # ~8 минут на видеокарте, сохраняет в data/brains/looking/
```

Мозг looking видит только геометрию цели, а его действия — повороты на
известные углы, поэтому его мир легко воспроизвести без Minecraft: цель
в случайном месте (близко/далеко, выше/ниже, сзади), стоит или бежит.
Симуляция за минуты даёт то разнообразие, которое вживую (боты стоят на
месте, цель — одна) не набрать и за часы: вживую мозг научился доворачивать
по горизонтали, но не выше/ниже — все боты стояли на одной высоте с целью.
Награда, мозг и файлы — те же, что у живого обучения; если мозг looking уже
есть, предобучение его дообучает. Живое обучение потом продолжает с этого места.

## Ускорение обучения: behavior cloning + DQfD

Чистый DQN стартует из рандома и долго не находит первый «+100» за подход
к цели. Поэтому поверх есть два механизма с твоих записей:

1. **Запись** — `npm run record`, бот-«призрак» `AI_Recorder` следит за
   твоим игроком и по команде `!rec start` пишет в
   `data/demonstrations.jsonl` пары «состояние → действия по каналам».
   Действия выводятся из дельт твоего игрока (обратная динамика), каналы
   независимо: ноги — пошёл вперёд → `walk_forward`, резкий поворот мышью →
   `turn_left/turn_right`, подпрыгнул в движении → `jump_forward`; голова —
   наклон → `look_up/look_down`, мелкий доворот → `look_left/look_right`;
   руки — взмах рукой (удар/копание) → `attack_center`. Остановить:
   `!rec stop`, статус: `!rec status`. Записывай непрерывными сессиями по
   5–10 минут. Старые записи (одно действие на тик) тоже читаются: действие
   уходит своему каналу, остальным — «ничего не делал».
2. **Офлайн-тренировка** — `python py/train_bc.py` (или `npm run train-bc`):
   тренирует сети всех каналов как классификаторы через cross-entropy, по
   эпохам пишет train/val accuracy, ранняя остановка при плато (но не
   раньше 500 шагов обучения — на маленькой записи иначе останавливалось,
   не успев начать). Для
   головы и рук печатается доля «idle» в val — точность ниже неё значит,
   что сеть хуже тупого «всегда стой». ~60–70% для ног — хороший
   результат для BC. Веса: `data/bc_<канал>.pt`.
3. **Warm start** — новый мозг задачки берёт `bc_<канал>.pt` для тех
   каналов, у которых ещё нет своего чекпоинта (и нет обученного мозга
   родственной задачки); DQN дальше доучивает их наградами.
4. **DQfD** — демо-переходы (с наградами, посчитанными модулем задачки
   по записанным состояниям) заливаются в память мозга при его создании
   (`train.demo_preload`) и навсегда остаются отдельным хвостом буфера:
   `train.demo_fraction` (0.25) каждого батча сэмплируется из них, плюс
   margin-loss не даёт Q действию эксперта просесть ниже остальных
   (`train.demo_margin`). Награды демо — не «слепая имитация», а честная
   специализация: walking наградит запись за подход к цели, gathering —
   за добычу.

Если дописываешь действия или входы В КОНЕЦ — мозги доращиваются сами.
Поменял размер сетки зрения (`vision.resolution`) — тоже: свёртки от
размера картинки не зависят, а слой, собирающий их выход, переносится на
новую сетку (`py/dqn.py: _grow_vision`). Задачки без зрения (looking)
после этого отвечают ровно как раньше, остальные начинают с приближения и
доучиваются (проверено на настоящих мозгах, 8x8 -> 16x16). Записи
геймплея с другим разрешением пропускаются.
Если меняешь `memory.frame_stack`, переставляешь скаляры или действия
(`CHANNELS`), меняешь формат наблюдения (`block_classes`, `entities`) —
старые `data/brains/*/*.pt`/`bc_*.pt` несовместимы, цикл это поймает
(`RuntimeError` при загрузке) и начнёт заново сам (только несовместимые
каналы). Несовместимый мозг не удаляется, а откладывается в
`data/brains_old/<задачка>_<дата>/` — вдруг настройки вернут. Старые
записи `demonstrations.jsonl` надо перезаписать (`npm run record`) —
train_bc и DQfD скажут об этом.

Лаунчер — тёмная или светлая тема (переключатель «Тёмная тема» в панели,
выбор запоминается в `data/launcher_settings.json`).

**Команды удобнее писать в строке команд лаунчера** (внизу лога): выбираешь
«Кому» (все или AI_N), набираешь команду — «!» можно не писать. При наборе
всплывают подсказки (команды, задачи, `player/position/none`, номера
ботов, ники, которые уже вводил): Tab — подставить, ↑↓ — выбрать, Esc —
скрыть; ↑↓ на пустой строке листают историю. Известная команда
подсвечивается зелёным, неизвестная — красным, под строкой — подсказка.
Ответы ботов приходят в лог (фиолетовым), чат игры не засоряется. Те же
команды по-прежнему работают и в чате игры.

Цель задаётся командой (главнее любого модуля, см. «Обучающие модули» выше):

```
!help
!setTarget player <username>
!setTarget position <x> <y> <z>
!setTarget none
!task <задача>       — сменить задачу этому боту (walking/looking/gathering/crafting)
!task all <задача>   — сменить задачу всему рою
!task follow         — любая задачка: walking/looking/follow/gathering/crafting/mix
!task all tag        — салки всем роем (один водит, остальные убегают)
!greedy [номер]      — бот (по умолчанию №1) перестаёт действовать случайно и
                       показывает, чему сети уже научились; повтор — выключить
!stop      — пауза ИИ у ВСЕХ ботов роя: тиковый цикл останавливается,
             состояния в Python не уходят (модель не учится на стоянии),
             действия не применяются
!resume    — продолжить работу ИИ
!debug     — позиция, углы, health/food, «на земле/в воздухе», номер тика
!entities  — ближайшие сущности: кто и на каком расстоянии
!whatYouSee
```

Обычный чат слышат ВСЕ боты роя, поэтому команда из него действует на
каждого (`!setTarget player <ник>` ставит цель сразу всем). Чтобы
обратиться к одному боту — личное сообщение: `/msg AI_3 !task looking`.
Исключение — `!greedy`: в общем чате реагирует только бот с указанным
номером. Пока epsilon высокий (первые часы), поведение роя почти
случайное — `!greedy` показывает, что сеть умеет на самом деле.

## Известные упрощения

- `walking` расставляет случайные точки (на текущей высоте Y бота) без
  проверки, достижимы ли они, — недостижимая ловится по счётчику «не
  приближаемся N тиков подряд» и перевыбирается. Путь к точке — маршрут
  A* (`js/route.js`), но идёт по нему сама сеть: маршрут лишь показывает
  ей ближайшую точку пути и меряет прогресс. Маршрут не знает про двери,
  лестницы, плавание и строительство — для него это стены.
- `gathering` не отслеживает сущности напрямую (Node их в `state` не
  шлёт) — источник награды один: рост `inventory_count`. Это одинаково
  ловит и сломанный блок, и дроп с убитого моба, но не различает их
  и не умеет штрафовать промах именно по мобу (только «удар в воздух»,
  когда в прицеле не было даже блока).
- `crafting` — интерфейс-заглушка, TODO с планом реализации лежит прямо
  в `py/training_modules/crafting.py`.

## Стиль кода / предпочтения автора

- Многословный, читаемый код — без чрезмерного сжатия/трюков.
- Не любит «переусложнённый» или явно AI-сгенерированный неряшливый код.
- Для несложных концептуальных частей предпочитает подсказки/наводящие
  вопросы, а не готовый код — хочет разобраться сам.
- **Исключение**: математика (углы, векторы, тригонометрия) — тут можно
  и нужно сразу давать готовый рабочий код.
- Предпочитает эмпирическую отладку (проверить логами/тестом) вместо
  теоретических рассуждений о причине бага.
